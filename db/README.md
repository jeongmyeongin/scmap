| 환경 | 상태 | 결과 |

| 실제 Supabase (2026-11-09, 사용자 실행) | **점검 SQL만 실행** | 점검 12항목 전부 OK. 동작 테스트 100개는 Supabase에서 미실행 (4단계에서 웹앱 연동 시 확인) |

## 2단계 보완 내용 (2026-11-09)

1. **제보 채택과 현장 검증 분리**: `review_field_report()` 채택 시 L4·`pending_review`로만 생성. `verified` 전환은 `verify_hazard_on_site()`로만 가능하며, 검증자·확인일·방법·측정값·근거(10자 이상)·이전 상태를 `hazard_verifications`에 남긴다. 이 이력은 누구도 직접 쓰거나 고치거나 지울 수 없다. 제한 유형은 실측값 필수, 육안 확인만으로 검증 불가, 제보자 본인은 자기 제보를 검증할 수 없다. 관리기관 공식 자료로 검증하면 L2, 실측이면 L1.
2. **verified 우회 차단**: verified로 바로 INSERT 불가. verified 전환·verified 상태의 값·좌표·유형·등급 변경은 같은 트랜잭션에서 기록된 현장 검증 이력이 있어야만 허용.
3. **현장 제보 검증**: 제보에도 대한민국 좌표 범위, 유형별 측정값 범위, 제한 유형 값 필수, 미래 측정일 금지 적용. 위험정보와 같은 검사 함수를 써서 규칙이 어긋나지 않게 했다. 오류 제보는 저장 자체가 안 되므로 채택 과정에서 위험정보로 넘어갈 수 없다.
4. **값 규칙 강화**: 공사·일방통행·진입곤란지역처럼 값이 없어야 하는 유형에 값이 들어오면 오류로 거부 (기존에는 허용).
5. **Supabase 호환**: PostGIS를 `extensions` 스키마에 설치 [확인: Supabase PostGIS 문서], 함수 검색 경로에 `extensions` 포함, 쓰기 함수의 실행 권한을 비로그인에서 회수 [확인: Supabase 문서 — 새 함수는 기본적으로 모든 역할이 호출 가능].

## 최초 관리자 등록 (Supabase SQL Editor)

관리자만 프로필을 만들 수 있으므로, 첫 관리자는 **Supabase 대시보드의 관리자 DB 권한**으로 한 번만 등록한다. 앱 안에는 관리자 권한을 얻는 경로를 만들지 않았다.

1. 대시보드 **Authentication → Users**에서 관리자로 쓸 계정을 추가한다 (이메일·비밀번호).
2. 추가된 사용자의 **User UID**를 복사한다.
3. **SQL Editor**에서 실행한다 (UID와 표시명만 바꿈):

```sql
insert into public.profiles (user_id, display_name, role, is_active)
values ('여기에-복사한-UID', '관리자(직위)', 'admin', true);
```

4. `supabase/precheck.sql`을 실행해 12번 항목(활성 관리자 수)이 OK인지 확인한다.

이 방법이 동작하는 이유 [판단]: SQL Editor에는 로그인 사용자 토큰이 없어 `auth.uid()`가 비어 있고, 테이블 소유자(postgres) 권한으로 실행된다. 로컬에서는 T94로 같은 조건을 시뮬레이션해 통과했고, 실제 Supabase에서도 이 절차로 관리자 1명 등록을 확인했다 (점검 12).

우회 경로가 없는 근거 (로컬 테스트):

| 시도 | 결과 | 테스트 |
| --- | --- | --- |
| 신규 가입자가 본인 admin 프로필 생성 | 거부 | T90 |
| 신규 가입자가 viewer 프로필 자가 생성 | 거부 | T91 |
| 대원이 자기 역할을 admin으로 변경 | 거부 | T44 |
| 열람자가 다른 사용자를 admin으로 변경 | 거부 | T92 |
| 검토자가 비활성 admin 계정 재활성화 | 거부 | T93 |
| 프로필 없는 사용자의 데이터 조회 | 0건 | T89 |

주의:
- **service_role 키는 RLS를 우회한다** [확인: Supabase RLS 문서]. 브라우저 코드, GitHub, 채팅 어디에도 올리지 않는다.
- 새로 가입한 사용자는 관리자가 프로필을 만들어 주기 전까지 아무것도 볼 수 없다. 원치 않는 가입을 막으려면 Auth 설정에서 신규 가입 허용을 끄는 것을 권장한다 (메뉴 위치 [요확인]).
- 관리자 계정을 모두 잃으면 같은 SQL Editor 절차로 복구한다.

## Supabase 적용 전 점검표

| 점검 항목 | 확인 근거 | 로컬 | Supabase |
| --- | --- | --- | --- |
| PostGIS 확장 위치 = `extensions` | [확인] Supabase PostGIS 문서 | OK (점검 1) | OK |
| SQL 실행 순서 01 → 02 → 03 → 04 → precheck | 파일 간 의존성 [판단] | OK | OK (점검 1~11 통과로 확인) |
| `auth.uid()` 제공 | [확인] Supabase RLS 문서. 로컬은 흉내 함수 | OK (점검 2) | OK |
| 모든 테이블 RLS 활성 | — | OK (점검 3) | OK |
| 비로그인 테이블·쓰기 함수 권한 없음 | [확인] Supabase 기본 권한 문서 | OK (점검 4~7) | OK |
| 뷰 RLS 우회 방지 (security_invoker) | [확인] Supabase 문서: 뷰는 기본적으로 RLS 우회 | OK (점검 8) | OK |
| 최초 관리자 등록 | 위 절차 | OK (T94) | OK (점검 12: 활성 관리자 1명) |

로컬 흉내 파일과 실제 Supabase의 차이 [판단]: 로컬 `auth.uid()`는 `request.jwt.claim.sub`만 읽는다. 실제 Supabase 함수는 Supabase가 제공하므로 이 파일을 실행하지 않는다. Supabase에서 PostGIS를 `public` 스키마에 설치했다면 `spatial_ref_sys` 테이블 때문에 점검 3번이 "확인 필요"로 나올 수 있다.
